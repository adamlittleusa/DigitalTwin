# Twin Deployment Design

Sub-project 3 of adambuilds.ai. Approved in conversation on 2026-09-06.

## 1. Goal

Run the twin API on Fly.io at `https://api.adambuilds.ai`, on exactly one
always-on machine, with secrets held by Fly, a certificate Fly manages, tests
on every pull request, and a deploy that happens by itself when a change
merges to `main`.

## 2. Context

Sub-project 2 (PR #2, merged 2026-09-06) produced the API and a Docker image
that bundles only the reviewed knowledge. Its spec chose Fly.io on one small
always-on machine because the rate limits, the daily budget, and the
in-flight cap live in process memory; a second machine would double them.
The domain `adambuilds.ai` is registered at GoDaddy on GoDaddy's default
nameservers and has never been configured. Adam created a Fly.io account
under his email on 2026-09-06. `flyctl` is not installed on the authoring
machine; `gh`, Docker, and Node are.

The site (Next.js on Vercel) does not exist yet. The API can go live first:
without a site there is nothing to call it from a browser, and the limits
already protect it from direct callers.

## 3. Decisions

| Question | Decision |
|---|---|
| Host | Fly.io, app `adambuilds-twin`, primary region `bos` (Boston). |
| Instances | Exactly one `shared-cpu-1x` machine with 512 MB, always on. No autoscaling, `--ha=false` on every deploy. |
| Build | Fly's remote builder builds the existing `apps/twin/Dockerfile` from the repo root. No image registry of our own. |
| Deploys | GitHub Actions: tests on every pull request; on a push to `main`, tests then `fly deploy`, then a health smoke against the public URL. First deploy from Adam's laptop. |
| Domain | `api.adambuilds.ai` as a CNAME at GoDaddy to `adambuilds-twin.fly.dev`; certificate issued and renewed by Fly. Apex and `www` untouched until the site spec. |
| Secrets | `OPENAI_API_KEY`, `PUSHOVER_USER`, `PUSHOVER_TOKEN`, `TWIN_LOG_SALT` as Fly secrets. Everything else is plain config in `fly.toml`. |
| Client address | When the proxy is trusted, prefer a configurable client-IP header (`Fly-Client-IP` on Fly), else the last `X-Forwarded-For` hop, else the peer. |
| Logs | Fly's built-in logs and their short retention. That is the retention decision the API spec deferred: withheld or failed notifications log the visitor's email, and it ages out within days. |
| Spend | The app's 500-call day is the guard on the model. Adam sets a monthly usage limit on his OpenAI account as a manual step. |

## 4. Out of scope

- The site, Vercel, and DNS for the apex and `www`.
- A web application firewall, geo-blocking, multiple regions, a second machine.
- Metrics dashboards and paging. Fly's health check restarts a failing machine; that is the alerting.
- Rewriting git history. The history scan in section 10 only reports.

## 5. The Fly app

`fly.toml` lives at the repo root so the build context is the repo root, which
the Dockerfile expects (`COPY apps/twin/...`, `COPY knowledge/...`). Fly
honours the root `.dockerignore`, so `.env`, `knowledge/raw/`, `private/`, and
`docs/` never leave the machine. The file is hand-written, not generated by
`fly launch`, so it says exactly what we mean:

```toml
# Fly.io configuration for the twin API. The build context is this directory, the repo root.
app = "adambuilds-twin"
primary_region = "bos"

[build]
  dockerfile = "apps/twin/Dockerfile"

[env]
  TWIN_TRUST_PROXY = "true"
  TWIN_CLIENT_IP_HEADER = "Fly-Client-IP"
  TWIN_ALLOWED_ORIGINS = "https://adambuilds.ai,https://www.adambuilds.ai"
  TWIN_SITE_URL = "https://adambuilds.ai"

[http_service]
  internal_port = 8080
  force_https = true
  auto_stop_machines = "off"
  auto_start_machines = true
  min_machines_running = 1

  [http_service.concurrency]
    type = "requests"
    soft_limit = 25
    hard_limit = 50

  [[http_service.checks]]
    grace_period = "15s"
    interval = "15s"
    timeout = "5s"
    method = "GET"
    path = "/v1/health"

[[vm]]
  size = "shared-cpu-1x"
  memory = "512mb"
```

Notes on the choices:

- The image already sets `KNOWLEDGE_DIR=/app/knowledge`, `TWIN_HOST=0.0.0.0`,
  and `PORT=8080`; Fly's `internal_port` matches.
- `auto_stop_machines = "off"` with `min_machines_running = 1` keeps the one
  machine up. `auto_start_machines` is left on so Fly restarts it after a
  host event.
- Fly's concurrency limits are per machine and count requests; they sit above
  the app's own `MAX_IN_FLIGHT = 8` for chats so health and project requests
  are never queued behind conversations.
- The health check is the API's own `/v1/health`. A machine that fails it is
  restarted by Fly.
- 512 MB rather than 256 MB: the process holds a 10,000-token prompt, the
  OpenAI client, and one worker thread per in-flight chat; 256 MB is close to
  the line and the difference is about two dollars a month.
- `fly deploy` creates two machines on a first deploy unless told otherwise.
  Every deploy in this spec passes `--ha=false`, and the runbook checks
  `fly scale show` reports one machine.

## 6. Configuration and secrets

| Name | Where | Value |
|---|---|---|
| `OPENAI_API_KEY` | Fly secret | From the laptop `.env`, imported without printing (section 9). |
| `PUSHOVER_USER`, `PUSHOVER_TOKEN` | Fly secrets | Same. |
| `TWIN_LOG_SALT` | Fly secret | 64 hex characters generated at import time; never reused elsewhere. Required because `TWIN_TRUST_PROXY=true`. |
| `TWIN_TRUST_PROXY` | `fly.toml` | `true`. Fly's proxy is the only thing that can reach the machine. |
| `TWIN_CLIENT_IP_HEADER` | `fly.toml` | `Fly-Client-IP`. New setting, section 7. |
| `TWIN_ALLOWED_ORIGINS` | `fly.toml` | The two site origins. A Vercel preview origin can be added later. |
| `TWIN_SITE_URL` | `fly.toml` | `https://adambuilds.ai`, the base for project-card links. |
| `TWIN_MODEL`, limits, `PORT`, `TWIN_HOST` | defaults or image | Unchanged. |

Secrets are set once from the laptop and never appear in the repo, the
workflow, or a log. The GitHub deploy token can deploy but cannot read Fly
secrets.

## 7. Code change: the client address behind a trusted proxy

`Settings` gains `client_ip_header: str = ""` from `TWIN_CLIENT_IP_HEADER`
(stripped; blank means unset). `client_key(request, settings)` becomes:

1. If `settings.trust_proxy` and `settings.client_ip_header` is set and the
   request carries that header with a non-empty value, return it.
2. Else if `settings.trust_proxy` and `X-Forwarded-For` has a non-empty last
   hop, return that.
3. Else the peer address, or `"unknown"` with a warning.

Fly sets `Fly-Client-IP` on every request it proxies and strips any value a
client sends, so on Fly the key cannot be forged. Off Fly the setting is
blank and behaviour is unchanged. Tests cover the header present, the header
configured but absent (falls to the last hop), and the setting blank (header
ignored even if present).

## 8. CI and deploys

One workflow, `.github/workflows/twin.yml`:

```yaml
name: twin

on:
  pull_request:
  push:
    branches: [main]
    paths:
      - "apps/twin/**"
      - "knowledge/**"
      - "evals/**"
      - "fly.toml"
      - ".dockerignore"
      - ".github/workflows/twin.yml"
  workflow_dispatch:

jobs:
  test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: apps/twin
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
        with:
          python-version: "3.13"
      - run: uv sync --frozen
      - run: uv run ruff check .
      - run: uv run pytest --cov=twin

  deploy:
    needs: test
    if: github.event_name != 'pull_request'
    runs-on: ubuntu-latest
    concurrency:
      group: twin-deploy
      cancel-in-progress: false
    steps:
      - uses: actions/checkout@v4
      - uses: superfly/flyctl-actions/setup-flyctl@master
      - run: flyctl deploy --remote-only --ha=false
        env:
          FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}
      - name: Smoke the public URL
        run: |
          expected=$(find knowledge -name '*.md' -not -iname 'readme.md' -not -path 'knowledge/raw/*' | wc -l)
          body=$(curl -fsS --retry 6 --retry-delay 10 --retry-all-errors https://api.adambuilds.ai/v1/health)
          echo "$body"
          echo "$body" | grep -q '"status":"ok"'
          echo "$body" | grep -q "\"knowledge_files\":$expected"
```

What it means:

- Every pull request runs ruff and the unit suite with the 80 percent
  coverage gate. The paid evals never run in CI: `pytest`'s default deselects
  them and no OpenAI key exists in GitHub. The live test skips itself.
- A push to `main` that touches the app, the knowledge, the evals, or the
  deploy files runs the tests and then deploys. Docs-only merges do nothing.
  `workflow_dispatch` gives a manual redeploy button.
- Deploys never overlap (`concurrency` on the job) and never cancel a running
  deploy.
- The smoke step proves the public hostname, TLS, and the new image answer,
  and that the image holds every committed knowledge file. It makes no model
  call, so it costs nothing and cannot notify.
- `FLY_API_TOKEN` is a deploy-scoped token (`fly tokens create deploy`) stored
  as a repository secret. It is created on Adam's laptop and piped straight
  into `gh secret set`, so it is never displayed.

## 9. First deploy, a runbook

Manual steps are marked **Adam**; the rest are run in the plan with Adam
present. Nothing prints a secret.

1. **Adam**: confirm the Fly account has a payment method (Fly will not start a machine without one).
2. Install `flyctl` on the laptop with Fly's PowerShell installer; **Adam** runs `fly auth login` (opens a browser).
3. `fly apps create adambuilds-twin` (the name is global; if taken, pick `adambuilds-twin-api` and update `fly.toml` and the CNAME target below).
4. Import secrets from the laptop `.env` without printing them:
   `grep -E '^(OPENAI_API_KEY|PUSHOVER_USER|PUSHOVER_TOKEN)=' .env | fly secrets import --stage`
   then `fly secrets set --stage TWIN_LOG_SALT=$(python -c "import secrets; print(secrets.token_hex(32))")`.
   (`--stage` defers the restart until the first deploy.)
5. `fly config validate`, then `fly deploy --remote-only --ha=false`. Confirm `fly scale show` reports one machine in `bos` and `curl https://adambuilds-twin.fly.dev/v1/health` answers.
6. **Adam**: at GoDaddy, DNS for `adambuilds.ai`, add a CNAME record: name `api`, value `adambuilds-twin.fly.dev`, TTL 600.
7. `fly certs add api.adambuilds.ai`, then `fly certs check api.adambuilds.ai` until it reports issued (minutes once the CNAME resolves).
8. Acceptance from the public URL: health over TLS, one streamed chat with `curl -N` to `POST /v1/chat` ("Where are you based?"), and the Corelight question to see the shared label and the deflection. Two pushes may reach Adam's phone if the model records anything; the chosen questions should not.
9. **Adam**: `fly tokens create deploy -x 8760h | gh secret set FLY_API_TOKEN` (one year; renew by rerunning). Never paste the token anywhere.
10. Merge the deployment branch. The workflow deploys and its smoke step passes. Confirm in the Actions tab.
11. **Adam**: set a monthly usage limit on the OpenAI account.

## 10. Safeguards inherited from the earlier specs

- **Reviewed dates.** A unit test loads the committed `knowledge/` tree and
  fails if any file lacks a `reviewed` date, naming the files. It runs in CI,
  so an unreviewed file cannot merge. As of this spec
  `knowledge/projects/digital-twin.md` has no date; **Adam** reviews it and
  sets one, or the test blocks the deploy branch.
- **History scan.** Before the first deploy, a read-only scan of the git
  history of `knowledge/` for the names and details struck during Adam's
  reviews (the term list comes from the local, uncommitted review notes and
  is never written to the repo). The history is already public, so the scan
  can only report; if it finds something, whether to rewrite history is a
  separate decision for Adam and is not part of this spec.
- **No raw content in the image.** Already enforced by `.dockerignore` and
  verified in sub-project 2; the smoke step's file count is a second check.

## 11. Operations

- **Logs**: `fly logs`; the app's JSON turn lines are there. **Status**: `fly status`, `fly checks list`.
- **Rollback**: `fly releases` lists releases; `fly deploy --image <previous image> --ha=false` reinstates one. Reverting the merge on `main` also redeploys.
- **One machine, always**: `fly scale count` is never run above 1; the deploy flag `--ha=false` is in the workflow and the runbook. If a second machine ever appears, the limits are wrong until it is removed.
- **Cost**: about three to four dollars a month for the machine and Fly's shared IPv4; the certificate is free; GitHub Actions is free for a public repository.
- **Restarts**: Fly restarts the machine on a failed health check; the app has no state to lose beyond the in-memory limits.

## 12. Verification

Tested without Fly:

- `client_key` with the configured header, without it, and with the setting blank.
- The reviewed-date test against the real tree.
- `fly config validate` on `fly.toml` (needs `flyctl`, no account).
- The workflow file parses (`actionlint` if available, otherwise a YAML load).

Acceptance, manual and in this order: the machine is up on Fly with one
instance; `https://api.adambuilds.ai/v1/health` answers over TLS with the
knowledge file count; a streamed chat works from the public URL; a merge to
`main` deploys by itself and the smoke step passes; `fly logs` shows the JSON
turn lines and nothing that looks like a secret.

## 13. Risks

- **A second machine.** Fly defaults and a stray `fly scale` could add one, doubling the limits. Mitigation: `--ha=false` everywhere, the runbook check, and the rule in section 11.
- **Log retention.** Visitor emails in withheld-notification lines live only as long as Fly keeps logs. Accepted; it is also the privacy-friendly default.
- **The deploy token.** Stored in GitHub; it can deploy but not read secrets. Rotate by rerunning step 9. If the repo were compromised, the worst case is a bad deploy, reverted by rollback.
- **Cold start on restart.** A restart costs a few seconds of downtime and resets the limits. Accepted for a portfolio.
- **Free-tier changes.** Fly's pricing changes over time; the machine is small enough that the exposure is dollars.
- **Header trust.** `TWIN_TRUST_PROXY=true` is only correct behind Fly. The same `fly.toml` is never used for a local run.
